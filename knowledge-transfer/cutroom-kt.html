Cutroom in one page

Cutroom is a local reel-creation engine. A caller hands it a narrated brief — sentences, claim labels, visual criteria, a style and a spending ceiling. Cutroom plans the reel, makes and checks still pictures, turns them into short clips, narrates and captions them, and returns one measured MP4. It runs as one Node process on one machine, listens only on 127.0.0.1, and keeps every row it needs to inspect, cancel or resume a run in one SQLite file.

The shape of it, in five sentences

  1. The API stores, the worker works. POST /v1/runs validates the body against @cutroom/reel-contract, writes a run row and one queued reel.plan job, and answers 202. Nothing else happens in the request. (lifecycle)
  2. The queue is a table. One worker polls job every 500 ms, claims the oldest due row with a single UPDATE … RETURNING, runs it, and each job enqueues the next one in the chain. (database & queue)
  3. Stages are pure. packages/pipeline holds planReel, makeStills, makeClips, cutReel and the gates. They import no database, no file system and no adapter; they are handed ports. (pipeline stages)
  4. Spending is wrapped. The worker wraps every port it was handed: a guard compares the reel's spend against the per-reel cap and the caller's ceiling before every paid call, and every call that returns writes a receipt row. (budget, ports)
  5. Only the composition root chooses adapters. apps/service reads CUTROOM_* settings, builds each port through packages/providers (the only place a key is read), applies migrations, then starts the API and exactly one worker. (settings)

What Cutroom is not

  • Not hosted. Loopback only, no authentication — whoever reaches 127.0.0.1 owns the machine (D-098). Not a setting.
  • Not a general video editor. The cut assembles the clips this engine made; nothing else.
  • Not on a registry. @cutroom/sdk and @cutroom/reel-contract are built to tarballs by scripts/package-sdk.mjs; the engine itself is never packaged.
  • Not KnowScroll. The script, the claims' evidence and the player live in the steering repository's world. Cutroom receives labels, never evidence (D-096).
  • Not free by accident. Every port defaults to the fake stand-in; only scripts/real-reel.mjs, run by a person who types the ceiling back, spends money.
  • Not concurrent. Exactly one worker, one job at a time (S-113).

High-level design

System map

Every runtime piece and every line between them. Boxes are drag-able; drag the background to pan, Ctrl+scroll or the buttons to zoom. Click a box for what it owns, its files, what it may not do, and where to look when it breaks. Click a legend chip to hide a kind of line.

Reading the map

One process, two halves

The service process holds the API (HTTP) and one worker (polling loop). They share nothing in memory but a ready getter; each opens its own SQLite connection (WAL mode, 5 s busy timeout).

Ports are the seam

Pipeline stages call interfaces from packages/contracts. The service builds implementations in packages/providers; the worker wraps them (guards, receipts, retries) and hands them to the stages.

Files are first-class

Pictures, clips, audio, frames and the final MP4 live under .artifacts/; results return paths, never bytes. The cap is read from BUDGET.md; owner questions are appended to QUESTIONS.md.

How the rules are kept honest

node scripts/drift.mjs

Runs dependency-cruiser over the real graph (146 modules today) and fails on any violation. Also scans for key-shaped environment reads outside packages/providers/src — the half of keys-only-in-providers an import graph cannot see.

drift.mjs --prove

Writes a deliberate violation of every rule — relative and by package name, npm packages laid out the way pnpm lays them out — and fails if any case stays silent, or a legal import is reported. A rule that reads right and matches nothing is the worst state.

drift.mjs --audit

Fails once a package has source while a folder one of its rules names is missing — what a rename looks like. split/ and plan/ exist, so every folder rule is live.

Entry rule. A package is entered only through its src/index.ts. Adding a package's first file also means adding its reference to the root tsconfig.json — tests/workspace.test.ts fails otherwise.

until:

Invariants the whole chain keeps

  • Every write that numbers an event is one immediate transaction — the event's seq and the row that carries it cannot be separated (packages/domain/src/runs.ts).
  • Receipts are written as calls return, outside the finishing transaction, so a later throw cannot erase what was spent (D-005, D-084).
  • Cancel is read in the same transaction as stage.started (startStage), before every job attempt. A cancel mid-stage takes effect at the next job.
  • A job that ends a run writes run.finished, the result and job.state = done together. A worker that dies between jobs leaves a queued job, never a half-finished run.
  • No port that buys reaches reel.assemble (I-18): its context holds model, media and assembler only.
  • Ids carry the attempt (a<attempt>-shot-<unit>-…), so a re-claimed job never reuses an id, a file path or a seed.

Pipeline stages, decision by decision

Each stage is a pure async function in packages/pipeline that never rejects: a thrown call, a refused parse or a bug becomes a failed outcome carrying everything made before it. The worker job maps the outcome to one domain function. Choose a stage:

Quality checks

The gates

GATE_ORDER = ['0', '1', '1S', '2', '3', '4', '5', '7'] (packages/pipeline/src/gates/index.ts). No Gate 6 — it would judge a join, and every reel is a cut (S-067). No Gate 8 — it is KnowScroll's (S-068). Exactly one gate profile exists, phase-1; a worker handed another refuses to start (D-052).

The rule behind every model-judged gate: the model judges, code decides. A witness (observe) describes what it sees and is never shown the brief (I-8). A reconciler (structured) holds that observation against the shot's subjects and criteria and answers fixed fields. Then plain code turns those fields into accept/fail with reasons. Every refused answer is kept in refused_answer and asked once more, told only its schema's issues (S-156).

Gate failure vs. thrown failure

A gate says no

The stage returns stopped-rule (or degrades/holds a shot and carries on). The run ends status: 'stopped', reason: 'rule', rule: 'gate-N', step. Nothing is resumed automatically; a caller may resume a Gate 7 stop.

Something throws

The stage catches it and returns failed with failure = failureKindOf(error), decided by the error's class. The run ends status: 'failed'; the kind goes in run.failure, not in the result. See failures & resume.

Hexagonal seam

Ports, adapters and the wrappers between them

A port is an interface in packages/contracts. An adapter implements it in packages/providers. apps/service turns one setting per port into an adapter through packages/providers/src/ports.ts; apps/worker receives the built ports, wraps them, and hands the wrapped ones to the stages. Stages never see an adapter, and the worker cannot import one (worker-no-providers).

Real adapters

MiniMax — minimax/

  • model.ts: POST /v1/chat/completions (OpenAI-compatible) with fetch + zod, no SDK (S-114). Strips reasoning blocks and fences; throws Spent with refused when the answer is not the schema.
  • narration.ts: POST /v1/t2a_v2, speech-2.8-hd, hex audio in the body plus a presigned subtitle_file URL for word timings — two calls per narration.
  • wire.ts: shared base URL, base_resp transient codes. One key: MINIMAX_KEY.

fal — fal/

  • queue.ts: submit to queue.fal.run/<slug>, poll status, fetch result. Two hosts (queue, storage) = two settings.
  • image.ts: entry from the closed IMAGE_REGISTRY; text wire for a canonical (no reference), edit wire otherwise. Frame read from the file's bytes (frame.ts), never trusted from the body.
  • video.ts + h3.ts: fal-ai/minimax-h3-turbo/{image,text}-to-video, always 768P, whole seconds 5–15, 0.5¢/s, 10-minute wait. upload.ts puts local pictures on fal storage. One key: FAL_KEY.

ffmpeg — ffmpeg/

  • tools.ts: ffmpeg/ffprobe found on PATH by name, always an argument array, ready() checks encoders and filters.
  • media.ts: real probe, black/frozen/silence scan and frame strip. Its readText and listen answer from a script (default: no words, no speech, no music).
  • assemble.ts: one invocation, one filtergraph, concat filter, burned captions, zoompan push on held shots.
  • sensors.ts: sharpness/brightness/similarity by filters; text via the model call it is handed. No key.

Picture frame: PICTURE_FRAME = 864 × 1536 (short side ≥ 768). Output profile: 768 × 1366, h264/aac, 24 fps, 48 kHz stereo. A slug outside the registry is refused by imageEntry() before any port is built. With a real image port the worker prices at the entry's own rate (S-124).

Stand-ins — providers/src/fake/

Every port's default is 'fake' (STAND_IN). Stand-ins write real PNG, MP4 and WAV files under the artifact root, so ffmpeg measures them for real. They answer from CUTROOM_STAND_IN_SCRIPT (a JSON object with optional model, images, sensors, video, narration, media). The stand-in model throws without a script — it never invents a plan — so an unscripted service can serve readiness and refusals but cannot finish a reel. fake/thrown.ts lets a script throw the exact error classes a real adapter would, which is how failure kinds are tested without a network.

Persistence

Tables, the queue and the lease

SQLite through Drizzle (packages/domain/src/schema.ts), opened by openDatabase with journal_mode = WAL, foreign_keys = ON, busy_timeout = 5000, and migrated from db/migrations/0000…0007 on every open. Default file: data/cutroom.sqlite (gitignored). Every time is an ISO-8601 UTC string; every JSON value is text. Click a table.

The job queue (D-002)

The claim is one statement, so two pollers can never take the same row:

UPDATE job SET state = 'running', attempts = attempts + 1,
               locked_at = :now, lease_until = :now + leaseMs
WHERE id IN (
  SELECT id FROM job
  WHERE kind IN ('reel.plan','reel.keyframes','reel.clips','reel.assemble')
    AND ( (state = 'queued'  AND run_at      <= :now)
       OR (state = 'running' AND lease_until <= :now) )
  ORDER BY id ASC LIMIT 1)
RETURNING *;
  • Oldest first, so a reel's job always runs before the job it creates.
  • Nothing renews a lease. A job still running when its lease expires is treated as abandoned, claimed again and run from the start (S-027). With real adapters the lease is a 4-hour floor, computed: 18 clips × 600 000 ms + 3 600 000 ms.
  • A throw escaping a job runner buries the job (buryJob: state = 'dead', error kept). Stages never throw, so this only catches bugs in the job glue — a dead job usually means a run left running.
  • cost_cents on each job is the running sum of its receipts; spentCents(runId) = SUM(cost_cents) over the chain (correlation_id = runId).

kind Enqueued by parent_id Ends with

Domain write functions — every one an immediate transaction

Events a caller reads (run_event)

type Fields Written when
run.accepted — submitRun, resumeRun
stage.started stage: plan | stills | video startStage, once per stage (not per attempt). reel.clips writes it for video; reel.assemble finds it already there.
verdict gate, outcome: accept | accept_with_label | fail, shotId? Gate 0 per plan row; Gate 1/1S per picture; 2–5 per take; 7 once

Every event carries contractVersion: 1, runId, seq (from 1 per run, never renumbered) and at. GET /v1/runs/:id/events?since=N returns events with seq > N and nextSince.

Recovery

How a run fails, and how it is made again

A failure's kind is decided by the class of what was thrown — never its message (failureKindOf, packages/contracts/src/failures.ts). The classes live in contracts because the adapters that throw them (providers) and the worker that catches them may not import each other.

FailureKind Comes from Engine resumes? Caller may resume?
unavailable Unavailable / StillUnavailable: 429, 5xx, connection error, timeout — after the transient counter's 3 sends yes yes
unreadable Spent (paid, unusable answer) or Unanswered (a gate's last ask refused) yes yes
provider-failed ProviderFailed: fal accepted the job, then reported it failed yes yes
crashed never thrown: the stills stage returns it when a re-claimed attempt cannot fit its pictures in 6 calls yes yes
off-spec OffSpec: the provider made something this engine may never use (a wrong frame) no no
engine anything else: plain Error, ZodError, fs, ffmpeg, RefusedRequest, an unreadable cap, a stand-in out of script no no

A cancelled run is never resumed by the engine. A caller may also resume a run that stopped at Gate 7.

A resume is a new run of the same request

Engine's own resume (apps/worker/src/resume.ts)

  1. Off in the worker's default; on in the service with delayMs = CUTROOM_RESUME_DELAY_MS (15 min).
  2. finishFailed reads the cap before the transaction (an unreadable cap becomes one line in QUESTIONS.md, not a buried job).
  3. The finishing function (finishRun/finishStills/finishVideo) runs the resume step inside SAVEPOINT resume, after the stage's labels and before run.finished: readResumeInputs → planResume(…, [], rates, 'engine') → admitResume → resumeRun.
  4. A step that throws rolls back to the savepoint: the run still fails, and one "could not be made" line is written after.
  5. Over the per-reel cap: the owner gets a question after the transaction. Over the caller's ceiling: nothing.

Caller's resume (POST /v1/runs/:id/resume)

  1. 404 if no run; then JSON, version, ResumeRequest schema (422 on failure).
  2. No ResumeService → 422 unsupported. The service always provides one.
  3. preview: true → reads through the connection, writes nothing, answers 200 with the four figures.
  4. Otherwise one immediate transaction: readResumeInputs → service.decide → resumeRun.
  5. service.decide is built by apps/service from the worker's own rates (resumeRates) — the API imports neither pipeline nor worker, yet both paths plan with one planner (S-174).

What resumeRun copies (packages/domain/src/resume.ts)

Copied, with kept_from = the failed run

  • every plan row
  • each kept picture (Gate 1 decided) with its observation and reconciliation — chosen reset, degradation kept
  • each finished narration
  • each decided take with its observation and reconciliation — degradation reset
  • run.accepted and the plan stage's events

Never copied

  • any receipt, lost_call, refused_answer — every cent stays with the run that spent it (D-084)
  • degradation, still_hold, render, hold — the new ending writes its own
  • files — a copied row keeps its stored path
  • a second resume: a run already resumed, or itself a resume, throws inside the transaction

The new run's first job is reel.keyframes (or reel.plan if the failed run had no plan), with no parent, due delayMs later, its attempts starting at the failed run's greatest for that kind — so every a<attempt>-… id and every seed is new (D-018, S-162).

Money

Two limits, checked before every paid call

The per-reel cap — the owner's

The Per reel, all-in row of steering-ref/steering/BUDGET.md — $3.00 = 300¢ today — read by readReelCapCents once per job attempt, never inside a transaction. Strict: a missing row or non-dollar figure throws (a cap that cannot be read is not a cap of 0). Hitting it asks the owner: an entry is appended to QUESTIONS.md after the run is finished (D-097, D-100).

The caller's ceiling — per request

options.budgetCents (integer, > 0). Hitting it returns a refusal or stop to the caller and nothing else — no question. When a call would pass both, the cap is named (limit: 'reel') because it is compared first.

Where each comparison happens

When Figure Against Code Outcome if over
Gate 0, each plan plan.estimateCents cap gate0 → cost plan fails Gate 0; all three over → refused / budget / reel + question
Admission, end of reel.plan stills: ⌈plannedImageCalls × imageRate⌉; video: estimateCents ceiling admitPictures / admitVideo refused / budget / ceiling, no question
Before every image call reel spent + image rate cap, then ceiling guardedImagePort answer refused → stopped / budget
Before every clip send reel spent + seconds × video rate cap, then ceiling guardedVideoPort same; question names the refused clip
Before every narration send reel spent + characters × rate (0 today) cap, then ceiling guardedNarrationPort same
A resume reel spent + resume estimate cap, then ceiling admitResume 409 budget (caller) / question (cap)

"Reel spent" (reelSpentCents) is the run's own chain plus, for a resume, the run it resumes — one reel, one cap, one ceiling. Exactly equal is admitted everywhere.

The estimate (D-083)

estimateCents = ⌈ plannedImageCalls × imageRateCents + Σ shot.durationSeconds × videoRateCentsPerSecond ⌉

plannedImageCalls ('recurring'):  0 if no subject recurs, else 2 + min(rankedSubjects − 1, 2)   → at most 4
plannedImageCalls ('upToThree'):  computed from the placement (canonical best-of-2 + one per other picture)
  • The reserve is not counted (S-035): a run may make at most 6 image calls in all (IMAGE_CALLS), the slots above the plan being repairs, each paid for as it is made and guarded then.
  • Narration is not in the estimate (rate 0 under MiniMax's token plan, D-019) and model calls cost nothing; receipts still record them.
  • Rates: pipeline defaults imageRateCents 15, videoRateCentsPerSecond 4. With real adapters the service substitutes the configured registry entry's rate and H3's 0.5¢/s — pre-flight must price what is actually configured (S-124, S-125).

Where every cent is written

Receipt rows

generation_receipt (image), video_receipt, speech_receipt, model_receipt — one per call that returned, with the rate applied.

Job cost

Each paid receipt's cost is added to the running job's cost_cents in the same transaction. A run's costCents is the sum over its chain.

Lost calls

A provider answered and the engine could not use it (Spent): a lost_call row and its cost on the job, then the error is rethrown unchanged (S-142). Image lost calls count toward the 6.

Public surface

The contract, the routes and the SDK

@cutroom/reel-contract (version 1) is zod schemas plus their inferred types. The API parses requests with them and the SDK parses responses with them, so both sides read one definition. Every object is strict: an unknown field is rejected, not stripped. Every top-level message and every event carries contractVersion: 1.

Routes (apps/api/src/server.ts, typed in routes.ts)

Route Answers Domain call SDK method
POST /v1/runs 202 accepted (replayed true/false) · 409 conflict · 422 version / invalid / unsupported · 500 submitRun submit(request)
GET /v1/runs?requestId= 200 RunStatus of the newest run for that id · 400 · 404 readRunByRequestId find(requestId)
GET /v1/runs/:runId 200 RunStatus · 404 readRun status(runId)
GET /v1/runs/:runId/events?since= 200 EventsPage · 400 (since not a whole number) · 404 eventsAfter follow(runId, since?)
GET /v1/runs/:runId/result 200 RunResult · 409 RunStatus while running · 404 readRun result(runId)
GET /v1/runs/:runId/record 200 RunRecord · 409 while running · 404 readRecord record(runId)
POST /v1/runs/:runId/cancel 200 RunStatus · 404 requestCancel cancel(runId)
POST /v1/runs/:runId/resume 200 preview · 202 accepted · 409 not-resumable / resumed / budget · 422 version / invalid / unsupported · 404 readResumeInputs, resumeRun resume(runId, body)
GET /v1/ready 200 {ready: true} once the worker started · 503 {ready: false} before none (a getter) used by createCutroom

Submit validates in order: JSON → object → contractVersion → schema → planVaryOn (only shotCount is built; the other three closed values answer 422 unsupported) — and only then the requestId, so an invalid body is 422 even when its id is known. Same id + same canonical JSON = replay of the newest run; same id + different content = 409.

What a caller sends — SubmitRequest

{
  contractVersion: 1,
  requestId: string,            // the caller's name for the reel
  worldId: string,
  narration: { text, claimIds[] }[],   // ≥ 4 sentences; one sentence is never split
  claims: { id, role: 'main' | 'supporting' }[],
  criteria: {
    mustShow:    Criterion[],
    mustNotShow: Criterion[],   // presence only
    depictionPolicyVersion: string,
  },
  style: { id, version: int ≥ 0, text },
  options: {
    until: 'plan' | 'stills' | 'video',
    budgetCents: int > 0,       // the caller's ceiling
    planVaryOn?: 'shotCount' | 'order' | 'canonicalSubject' | 'angle',
  },
}
Criterion = { id, text, type: 'presence' | 'event', claimId? }

Cross-field rules (superRefine)

  • a claim may be listed only once;
  • every claimIds entry must be a listed claim, and every listed claim must be referenced by some sentence (else no shot could show it — D-063);
  • a criterion's claimId must be a listed claim;
  • mustNotShow criteria must be presence (a still cannot prove an event did not happen — D-043);
  • planVaryOn: 'order' needs a main claim.
Practical minimum: 6 sentences. The schema accepts 4, but the default fork cuts the narration into 4 and 6 units without dividing a sentence; 4 or 5 sentences stop the run at the plan step with rule: 'split' before any model call.

The SDK — @cutroom/sdk

import { createCutroom } from '@cutroom/sdk'

const cutroom = await createCutroom({
  baseUrl: 'http://127.0.0.1:8787',   // default; loopback + explicit port only
  launcher: {                          // optional: started only if nothing answers
    command: process.execPath,
    args: ['--experimental-strip-types', '--no-warnings',
           'apps/service/src/main.ts'],
  },
  readyTimeoutMs: 30_000,              // positive whole number
})

const { runId } = await cutroom.submit(request)
let since = 0
for (;;) {
  const page = await cutroom.follow(runId, since)
  since = page.nextSince
  if ((await cutroom.status(runId)).state === 'finished') break
  await new Promise((r) => setTimeout(r, 1000))
}
const result = await cutroom.result(runId)
await cutroom.close()

Errors — three shapes

  • SdkApiError — a schema-valid ErrorResponse on a route's 400/404/500 arm; only the parsed body is exposed.
  • SdkProtocolError (stage: 'ready' | 'request') — unexpected status, bad JSON, body failing the route's schema; also every call after close(), and a request body failing SubmitRequest/ResumeRequest before any HTTP.
  • SdkConnectionError (stage: 'connect' | 'start' | 'ready' | 'close') — nothing listening and no launcher; child died before ready; readiness deadline; closing an owned child failed.

Joined vs owned

If a valid engine already answers /v1/ready, the handle is joined and close() only stops the handle. Otherwise the launcher spawns the command with shell: false, injects CUTROOM_API_PORT from the URL, and polls readiness; the handle is owned and close() writes stop to the child's stdin and waits. If the child exits early, the SDK re-probes: another consumer may have won the port race, and then the handle joins it.

Packaging: node scripts/package-sdk.mjs → .package-staging/cutroom-reel-contract-1.0.0.tgz and cutroom-sdk-1.0.0.tgz (ESM + .d.ts, Node ≥ 22.14). The workspace sources stay private/workspace:*; only the staged manifests are publishable. tests/cutroom-sdk-package-build.test.ts installs both into a fresh consumer outside the workspace.

Composition root

Settings, and the order the service starts in

apps/service/src/main.ts loads CUTROOM_ENV_FILE (default .env) underneath the process environment — a value exported by hand wins over a forgotten file — then readSettings(env) validates everything before anything is built. Defaults are found from the source file's own URL, never the working directory, so the service settles the same folders wherever it is started from (D-086).

Keys are not settings. MINIMAX_KEY and FAL_KEY are read only by packages/providers/src/env.ts (minimaxKey, falKey). The service passes the whole environment through; the banner prints adapter names and paths, never a key.

Startup sequence — every refusal happens before a job can be claimed

Stopping

Ctrl+C (SIGINT), or the line stop on standard input, or stdin closing. All three call the same stop(): close the API (dropping connections), then worker.stop(), which lets the job in hand finish before closing the database. The stdin route exists because Windows delivers no signal to a spawned child (S-118) — it is also how the SDK stops an owned engine.

When it breaks

Debugging guide

Start from the run's result, then its events, then its rows. Stages record every piece as it completes, so a failed run's tables hold exactly how far it got. Filter the symptom list:

Triage a finished run in five reads

  1. Result. GET /v1/runs/:id/result (or run.result). status + reason/rule/step/detail say which branch ended it. For failed, read run.failure for the kind.
  2. Events. GET /v1/runs/:id/events — the verdict and degraded sequence shows which shot and which gate.
  3. Jobs. job rows with correlation_id = runId: attempts > 1 means a lease expired and the job ran again; state = 'dead' + error means a bug in job glue.
  4. Pieces. picture.gate1 / gate1s JSON for stills; take.verdicts for clips; render.gate7 for the cut. Reasons are written in plain sentences.
  5. Provider answers. lost_call (paid, unusable) and refused_answer (the model's own words, redacted): node --experimental-strip-types --no-warnings scripts/refused.mjs <runId-prefix>. In a Claude session, the run-reader agent does steps 1–5 read-only.

Queries

-- the last runs and how each ended
SELECT run_id, request_id, state, failure, resumes,
       json_extract(result, '$.status') AS status, json_extract(result, '$.rule') AS rule,
       json_extract(result, '$.detail') AS detail
FROM run ORDER BY created_at DESC LIMIT 10;

-- a run's event log
SELECT seq, at, json_extract(body, '$.type') AS type, body FROM run_event WHERE run_id = :id ORDER BY seq;

-- its chain of jobs
SELECT id, kind, state, attempts, cost_cents, run_at, lease_until, error
FROM job WHERE correlation_id = :id ORDER BY id;

-- what it spent, by kind
SELECT 'image' AS kind, COUNT(*), SUM(cost_cents) FROM generation_receipt WHERE run_id = :id
UNION ALL SELECT 'video', COUNT(*), SUM(cost_cents) FROM video_receipt WHERE run_id = :id
UNION ALL SELECT 'speech', COUNT(*), SUM(cost_cents) FROM speech_receipt WHERE run_id = :id
UNION ALL SELECT 'lost', COUNT(*), SUM(cost_cents) FROM lost_call WHERE run_id = :id;

-- every picture and why Gate 1 decided as it did
SELECT seq, picture_id, role, label, json_extract(gate1, '$.outcome') AS outcome, gate1, gate1s, degradation, chosen
FROM picture WHERE run_id = :id ORDER BY seq;

-- every take and its gates
SELECT take_id, number, mode, outcome, verdicts, degradation FROM take WHERE run_id = :id ORDER BY shot_unit, number;

-- runs waiting to be picked up (e.g. an engine resume due later)
SELECT j.id, j.kind, j.run_at, r.run_id, r.resumes FROM job j JOIN run r ON r.run_id = j.correlation_id
WHERE j.state = 'queued' ORDER BY j.run_at;

Lessons from real runs — docs/reel-pitfalls.md

Brief-caused (most stops)

  • Long or tall subjects get clipped by the 9:16 frame and fail Gate 1 (P-002, P-012).
  • Things with lettering in life (cards, monitors, cities) trip a "no text" criterion (P-017).
  • Plural ids or "the pyramids" make the count rule fail (P-018).
  • A claim spanning two shots, criteria that fit one (P-008); a qualifier read as required (P-022).

Provider / network

  • fal's flux upstream 504 → run fails unavailable, resumable (P-009).
  • This machine's DNS times out on fal's IPv6 lookup → "fetch failed" (P-020).
  • MiniMax repeated a word in its timings (P-001); witness answered a count as words (P-004).

Engine

  • Gate 7's caption question refused a correct cut (P-011).
  • Gate 3's words and sound answer from the media port's script, so on a real run it has never heard a clip (P-007).
  • One clip's checks waited 14.5 min with no row saying where (P-024).
Playbooks

How to change things without breaking the rules

Gates before code. No implementation file for a feature whose four planning gates — product, architecture, program design, slices — are not approved by an adversarial reviewer, in docs/features/<slug>.md. Trivial fixes (one file, no new route, table, job or screen) skip to a slice. Any choice between real alternatives becomes an S- entry in DECISIONS.md: what was chosen, what was rejected, how a violation is caught.

Before you touch a test or a check

  • Never weaken a check or a test to reach green. If drift --prove fails, a rule stopped working — that is the finding.
  • Run the test-impact agent (or grep yourself) before changing a contract, a stand-in or a shared helper: many tests count exact calls, receipts and message text.
  • Stand-in model scripts are keyed by role and call order; adding a model call shifts every later answer in every scripted test that reaches it.

A feature's life

  1. Gates written in docs/features/<slug>.md: product, architecture, program design, slices — reviewed by the gate-reviewer agent (Opus), which may edit only the Gates: line.
  2. Slices built one at a time (the slice-builder agent hands back an uncommitted diff): tests first, code, one deliberate break per property seen red and restored.
  3. Journey: node scripts/journey.mjs <slug> after the last slice is committed — every check plus tests/<slug>-*.test.ts. PASS writes evidence and flips Status: verified; FAIL fills Divergence. Never typed by hand.
  4. Session close: a JOURNAL.md entry (the stop-gate hook refuses otherwise) and the matching entry in docs/context.md (tests/context-file.test.ts compares the two).

Features and their status

Environment traps, each already paid for

  • Node 22.14: TypeScript runs with --experimental-strip-types; pass test globs quoted and let Node expand them.
  • Windows, CRLF working tree, LF repository: Git Bash's sed/awk/grep strip \r and lie; count bytes with tr -cd '\r' < file | wc -c.
  • Backslashes can halve in transit through a heredoc — a regex \. silently matching any character once broke a boundary rule. Verify the file, not the command.
  • ffmpeg: always an argument array; a Windows path inside a filtergraph needs : and \ escaped, as an input/output argument it does not. Detectors report on stderr at info level.
  • No absolute paths, ever (D-086): one setting per generated path, default inside the repo; tests/no-absolute-paths.test.ts enforces it.
  • Never commit media, the SQLite file, generated artifacts or a secret.
